# Архитектура системы

## Принципы

1. **Backend считает, фронтенд рисует** — все расчёты, фильтрация, агрегация на сервере. Фронтенд только отображает данные. Это даёт производительность на слабых устройствах и при большом количестве вкладок.
2. **API-first** — фронтенд общается с бэкендом только через REST API. Никаких прямых запросов к БД.
3. **Не MVP** — каждая фича делается сразу на production-уровне. Фичи добавляются инкрементально, но каждая — полноценная.
4. **Монетизация** — платформа зарабатывает на подписках. Бесплатный уровень с ограничениями, платный — полный доступ.

## Потоки данных

### Сбор данных
```
MOEX ISS API → moex_client.py → repository.py → PostgreSQL (bonds)
```
Запускается по расписанию или вручную. Один запрос на борд, bulk upsert батчами по 500.

### Риск-сигналы эмитента (этап 1, подробно — docs/RISK_SIGNALS_PLAN.md)
```
цикл коллектора:
  fetch_all_bonds → snapshot_listing_changes → upsert_bonds → enrich_missing_inns
                     (diff list_level ДО апдейта)              (батч N бумаг без ИНН,
                     → issuer_events                            /iss/securities/{secid}
                                                                → issuers + bonds.issuer_inn)
```
- Смена уровня листинга фиксируется сравнением свежих данных MOEX с текущим состоянием БД **до** upsert'а.
- Дедупликация событий — уникальным ограничением `uq_issuer_event_fact (inn, type, date, source, secid)`.
- Обогащение ИНН идёт по одному запросу на бумагу с паузой (`ISSUER_ENRICH_DELAY_SECONDS`), батч на цикл — `ISSUER_ENRICH_BATCH`; ~3000 бумаг покрываются за несколько циклов и далее добираются только новые выпуски.
- API отдаёт риск-агрегат (`risk_events_count`, `has_severe_events`) одним outerjoin к сгруппированным событиям.

### Запрос пользователя
```
Браузер → React SPA → GET /api/v1/bonds?params → service.py → PostgreSQL → JSON → React → UI
```
Все расчёты (фильтрация, сортировка, пагинация, агрегация) — на бэкенде. Фронтенд получает готовые данные и рисует.

### Авторизация (планируется)
```
Браузер → POST /api/v1/auth/login → JWT token → localStorage → Authorization header
```

## Разделение ответственности

| Слой | Отвечает за | Не делает |
|------|------------|-----------|
| **Frontend (React)** | Отрисовка UI, роутинг, UX, формы фильтров | Расчёты, фильтрацию, прямой доступ к БД |
| **API (FastAPI)** | Валидация, авторизация, бизнес-логика, кэширование | Отрисовку, сбор данных с MOEX |
| **Collector** | Сбор данных с MOEX ISS, обновление БД | Обработку запросов пользователей |
| **PostgreSQL** | Хранение, индексы, constraints | Бизнес-логику |
| **Redis** | Кэш, сессии, rate limiting | Долгосрочное хранение |

## Масштабирование

- **Frontend** — статика, раздаётся через CDN/Nginx
- **API** — горизонтально, несколько инстансов за балансером
- **Collector** — один инстанс, CronJob
- **PostgreSQL** — вертикально, read replicas при необходимости
- **Redis** — вертикально, кластер при необходимости
