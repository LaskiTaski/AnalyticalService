# Фича «Риск-сигналы эмитента» — план реализации

> Статус: **этап 1 реализован** (июль 2026). Файл перенесён из стартового плана,
> раздел «Этапы» дополнен отметками и фактическими деталями реализации.

## Суть

Скринер уже показывает аномально высокие доходности (30–50%), но не объясняет их.
Добавляем к каждой бумаге бесплатные факты об эмитенте из открытых источников и
подсвечиваем **расхождение**: рейтинг говорит «нормально», рынок — «беда».
Рейтинг — не истина (урок 2008), а ярлык; сигнал — это разрыв между рейтингом и доходностью
плюс жёсткие факты (дефолты, банкротные сообщения, понижение листинга).

Никаких платных API и LLM-поиска: фоновые задачи парсят источники по расписанию в PostgreSQL,
фронтенд читает готовое из нашего API.

## Ключевая связка

У бумаги — SECID/ISIN, у эмитента — ИНН. Маппинг берём из MOEX ISS:
`/iss/securities/{secid}.json` → блок description содержит `INN` эмитента.
Таблица `issuers (inn PK, name, ogrn, okpo)` + `bonds.issuer_inn FK`.

## Модель данных

- ✅ `issuers(inn PK, name, ogrn, okpo)` — name на этапе 1 эвристика из имени бумаги
  (обрезка серии выпуска), заменяется каноническим на этапе 2
- ✅ `issuer_events(id, inn FK, type, date, title, url, source, secid)` — type:
  default, tech_default, bankruptcy_intent, listing_downgrade, listing_upgrade,
  state_support_request, offer, restructuring. Дедуп: `uq_issuer_event_fact
  (inn, type, date, source, secid)`
- ✅ `bonds.issuer_inn FK` (SET NULL)
- 📋 `issuer_ratings(inn, agency, rating, outlook, date, press_release_url)` — этап 2
- 📋 `issuer_financials(inn, year, revenue, net_income, debt, equity)` — этап 4 (ГИР БО)

## Скоринг «аномалии» (v1, без ML) — этап 2

Шкала рейтингов → ожидаемый диапазон доходности (спред к ключевой ставке).
Если фактическая доходность выше ожидаемой на N п.п. → бейдж:
- 🟡 «доходность выше типичной для рейтинга»
- 🔴 «рейтинг не отражает риск» (разрыв >15 п.п. или есть события default/bankruptcy_intent)

На этапе 1 вместо скоринга работает более простой агрегат: `risk_events_count` и
`has_severe_events` (default / tech_default / bankruptcy_intent / restructuring)
приходят в каждой бумаге одним outerjoin.

## Архитектурные решения этапа 1 (для контекста следующих этапов)

- Новые источники добавляются как модули в `backend/collector/` и вызываются из
  `run_collection()` либо отдельным циклом с другим интервалом; события пишутся
  в `issuer_events` через тот же `ON CONFLICT DO NOTHING` по `uq_issuer_event_fact`.
- «Тяжёлые» типы событий централизованы в `SEVERE_EVENT_TYPES`
  (`backend/db/models/issuer.py`) — скоринг этапа 2 расширяет это место.
- Фронтенд: метаданные типов событий — в `EVENT_META` (`IssuerTab.tsx`),
  подписи источников — в `SOURCE_LABEL` там же.
